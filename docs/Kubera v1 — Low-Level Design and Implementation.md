# Kubera v1 — Low-Level Design and Implementation

## 1. Purpose and scope

This document translates the Kubera v1 high-level design into an implementation-ready specification.
Kubera is a standalone, channel-agnostic MCP server for personal-finance transaction tracking. It is a single-user service in v1. The MCP client or AI agent is an untrusted conversational front end; Kubera owns validation, persistence, duplicate detection, audit history, and reporting calculations.
This document covers:

*   Go project structure.
    
*   SQLite schema and migrations.
    
*   Domain types and validation rules.
    
*   Application-service interfaces.
    
*   Repository interfaces and transaction boundaries.
    
*   MCP tool schemas and response conventions.
    
*   Duplicate-detection behavior.
    
*   Reporting queries and ordering.
    
*   Error handling, logging, configuration, and operations.
    
*   Testing and implementation sequencing.
    

The v1 scope is limited to money-in and money-out transactions, categories, corrections, voiding, duplicate detection, audit history, and reports. It does not include accounts, balances, bank synchronization, investment holdings, budgets, recurring rules, multi-user authorization, or permanent deletion.

## 3. Runtime and configuration

### 3.1 Configuration

Configuration should be loaded from environment variables, with explicit defaults only where safe.

```text
KUBERA_DATABASE_PATH       Required path to the SQLite database.
KUBERA_MCP_TRANSPORT       stdio for v1; reserve values for future transports.
KUBERA_LOG_LEVEL           debug, info, warn, or error; default info.
KUBERA_BUSY_TIMEOUT_MS     SQLite busy timeout; default 5000.
KUBERA_MAX_PAGE_SIZE       Maximum list page size; default 100.
KUBERA_MIGRATE_ON_START    true or false; default true.
```

The process should fail startup if the database path is missing, the parent directory is not usable, migrations fail, or required SQLite capabilities cannot be enabled.

### 3.2 Startup sequence

1.  Load and validate configuration.
    
2.  Initialize structured logging.
    
3.  Open SQLite.
    
4.  Configure foreign keys, WAL mode, busy timeout, and connection limits.
    
5.  Run pending migrations in a transaction.
    
6.  Verify the schema version.
    
7.  Construct repositories and application services.
    
8.  Register MCP tools.
    
9.  Start the MCP transport.
    
10.  On shutdown, stop accepting requests, allow in-flight requests to finish, close the transport, and close the database.
     

## 4. Domain model

### 4.1 Primitive types

Use explicit types rather than passing raw strings throughout the application.

```go
type TransactionID string
type CategoryID string
type AuditEventID string
type CurrencyCode string
type Direction string

const (
    MoneyIn  Direction = "money_in"
    MoneyOut Direction = "money_out"
)
```

IDs should be generated by the service before persistence. UUIDs are recommended. IDs are opaque to callers and must not encode timestamps or other sensitive information.
Amounts are signed neither in storage nor in API input. The direction determines whether an amount is money-in or money-out. `amount_minor` must be a positive 64-bit integer.

### 4.2 Transaction entity

```go
type Transaction struct {
    ID                    TransactionID
    Direction             Direction
    AmountMinor           int64
    Currency              CurrencyCode
    OccurredAt            time.Time
    CategoryID            CategoryID
    Description           string
    OriginalNotification  string
    ReferenceID           *string
    CreatedAt             time.Time
    UpdatedAt             time.Time
    VoidedAt              *time.Time
    VoidReason            *string
}
```

Persist and return timestamps in RFC 3339 format with an explicit UTC offset, preferably normalized to `Z`. All comparisons use UTC instants.

### 4.3 Category entity

```go
type Category struct {
    ID         CategoryID
    Name       string
    ArchivedAt *time.Time
    CreatedAt  time.Time
    UpdatedAt  time.Time
}
```

Category names are trimmed and compared case-insensitively for uniqueness. The original display casing may be retained from the first creation or updated explicitly according to the service rule.

### 4.4 Audit entity

```go
type AuditEvent struct {
    ID         AuditEventID
    EntityType string
    EntityID   string
    Operation  string
    OccurredAt time.Time
    Previous   json.RawMessage
    Current    json.RawMessage
    Reason     *string
}
```

Audit payloads must be JSON objects containing stable field names. Sensitive notification text should be omitted from audit payloads unless the product explicitly requires it.

## 5. SQLite schema

### 5.1 Migration 0001: initial schema

```sql
CREATE TABLE schema_migrations (
    version INTEGER PRIMARY KEY,
    applied_at TEXT NOT NULL
);

CREATE TABLE categories (
    id TEXT PRIMARY KEY NOT NULL,
    name TEXT NOT NULL,
    name_normalized TEXT NOT NULL,
    archived_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    CHECK (length(trim(name)) > 0)
);

CREATE UNIQUE INDEX categories_active_name_unique
    ON categories(name_normalized)
    WHERE archived_at IS NULL;

CREATE TABLE transactions (
    id TEXT PRIMARY KEY NOT NULL,
    direction TEXT NOT NULL CHECK (direction IN ('money_in', 'money_out')),
    amount_minor INTEGER NOT NULL CHECK (amount_minor > 0),
    currency TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    category_id TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    original_notification TEXT NOT NULL DEFAULT '',
    reference_id TEXT,
    normalized_description TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    voided_at TEXT,
    void_reason TEXT,
    FOREIGN KEY (category_id) REFERENCES categories(id),
    CHECK (length(currency) = 3),
    CHECK ((voided_at IS NULL AND void_reason IS NULL)
        OR voided_at IS NOT NULL)
);

CREATE TABLE audit_events (
    id TEXT PRIMARY KEY NOT NULL,
    entity_type TEXT NOT NULL,
    entity_id TEXT NOT NULL,
    operation TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    previous_json TEXT,
    current_json TEXT,
    reason TEXT
);

CREATE INDEX transactions_occurred_at_idx
    ON transactions(occurred_at);

CREATE INDEX transactions_category_occurred_idx
    ON transactions(category_id, occurred_at);

CREATE INDEX transactions_reference_idx
    ON transactions(reference_id)
    WHERE reference_id IS NOT NULL;

CREATE INDEX transactions_active_occurred_idx
    ON transactions(voided_at, occurred_at);

CREATE INDEX audit_entity_idx
    ON audit_events(entity_type, entity_id, occurred_at);
```

Store timestamps as canonical UTC RFC 3339 strings. Application code must always bind parameters and must not build SQL by string concatenation.

### 5.2 Migration rules

*   Migrations are embedded in the binary or loaded from a versioned, immutable migrations directory.
    
*   Each migration has one integer version and is applied once.
    
*   Migration application is serialized by a database transaction.
    
*   Migrations must be backward-conscious where possible, but v1 does not require zero-downtime rolling upgrades.
    
*   Destructive schema changes require an explicit migration and backup guidance.
    

## 6. Repository interfaces

Repositories should expose domain-oriented methods while keeping SQL-specific details private.

```go
type TransactionRepository interface {
    Insert(ctx context.Context, tx *sql.Tx, t Transaction) error
    Get(ctx context.Context, q Queryer, id TransactionID) (Transaction, error)
    List(ctx context.Context, q Queryer, filter TransactionFilter) ([]Transaction, Page, error)
    Update(ctx context.Context, tx *sql.Tx, t Transaction) error
    Void(ctx context.Context, tx *sql.Tx, id TransactionID, at time.Time, reason *string) error
    FindByReference(ctx context.Context, q Queryer, referenceID string) ([]Transaction, error)
    FindLikelyDuplicate(ctx context.Context, q Queryer, candidate DuplicateCandidate) ([]Transaction, error)
}

type CategoryRepository interface {
    Create(ctx context.Context, tx *sql.Tx, c Category) error
    Get(ctx context.Context, q Queryer, id CategoryID) (Category, error)
    List(ctx context.Context, q Queryer, includeArchived bool) ([]Category, error)
    Update(ctx context.Context, tx *sql.Tx, c Category) error
    Archive(ctx context.Context, tx *sql.Tx, id CategoryID, at time.Time) error
}

type AuditRepository interface {
    Append(ctx context.Context, tx *sql.Tx, event AuditEvent) error
    ListForEntity(ctx context.Context, q Queryer, entityType, entityID string) ([]AuditEvent, error)
}
```

`Queryer` should be a small interface implemented by `*sql.DB` and `*sql.Tx`, allowing read methods to work inside or outside a transaction.

## 7. Service layer and transaction boundaries

### 7.1 Create transaction

`CreateTransaction` performs the following inside one write transaction where duplicate protection requires it:

1.  Validate request fields.
    
2.  Normalize description and reference ID for comparison.
    
3.  Verify that the category exists and is active.
    
4.  Search for a duplicate.
    
5.  If a duplicate is found, roll back or do not begin the write transaction and return a typed duplicate result.
    
6.  Generate the transaction ID and timestamps.
    
7.  Insert the transaction.
    
8.  Append a `created` audit event.
    
9.  Commit.
    
10.  Return the persisted transaction.
     

The operation must not write a second transaction when a likely duplicate is found. The MCP response should make the duplicate outcome explicit rather than presenting it as a normal creation.

### 7.2 Update transaction

Updates use the existing stable ID. The service must:

*   Load the current non-missing transaction.
    
*   Reject updates to a transaction according to the chosen v1 rule if it is already voided; the recommended rule is to reject all ordinary updates after voiding.
    
*   Validate all replacement fields.
    
*   Verify the replacement category is active.
    
*   Re-run duplicate detection if amount, direction, currency, timestamp, description, or reference ID changes.
    
*   Update the row and append one `updated` audit event in the same database transaction.
    
*   Return the updated canonical entity.
    

The original notification text is immutable through `update_transaction`.

### 7.3 Void transaction

Voiding is an atomic update plus audit insert:

1.  Load the transaction.
    
2.  If missing, return `transaction_not_found`.
    
3.  If already voided, return `already_voided` and the existing canonical transaction without adding another audit event.
    
4.  Set `voided_at` and optional `void_reason`.
    
5.  Append a `voided` audit event.
    
6.  Commit.
    

Voided transactions remain queryable by ID and in audit history but are excluded from reports and ordinary listings by default.

## 8. Validation rules

### 8.1 Common rules

*   Required strings are trimmed before validation.
    
*   Empty required strings are rejected.
    
*   Unknown enum values are rejected.
    
*   Currency is an uppercase ISO 4217 alphabetic code of exactly three characters.
    
*   Amount must be a positive integer minor-unit value and fit in signed 64-bit range.
    
*   Timestamps must include a timezone offset and must parse as valid RFC 3339 values.
    
*   Store all timestamps in UTC.
    
*   Reject dates outside the supported database/time representation range.
    
*   Limit description, notification, reference, and reason lengths to documented maximums to prevent accidental resource exhaustion.
    

Recommended limits:

```text
Description:            500 UTF-8 characters
Original notification:  10,000 UTF-8 characters
Reference ID:           256 UTF-8 characters
Category name:          100 UTF-8 characters
Void reason:            1,000 UTF-8 characters
```

### 8.2 Category rules

*   Category names must be unique among active categories after trimming and Unicode-aware case folding.
    
*   An archived category cannot be assigned to a new or updated transaction.
    
*   A category in use may be archived but not physically deleted.
    
*   Archiving is idempotent; repeated archive requests return the archived category without creating duplicate audit requirements unless explicitly specified.
    

## 9. Duplicate detection implementation

### 9.1 Normalization

Create a comparison representation without changing stored user-facing values:

*   Trim leading and trailing whitespace.
    
*   Unicode normalize where supported.
    
*   Case-fold for comparison.
    
*   Collapse runs of whitespace.
    
*   Remove obvious formatting differences from reference IDs only if the rule is documented.
    
*   Do not remove meaningful digits, signs, decimal information, or merchant words without a documented rule.
    

Store `normalized_description` for deterministic querying. Preserve `description` and `original_notification` exactly after input decoding, apart from any explicitly documented trimming policy.

### 9.2 Matching priority

1.  If a non-empty reference ID exists, find active transactions with the same normalized reference ID, currency, and direction. A reference match is a duplicate only when the reference is sufficiently identifying according to the configured policy.
    
2.  Otherwise match on:
    *   Direction.
        
    *   Amount in minor units.
        
    *   Currency.
        
    *   Normalized description.
        
    *   Occurrence time within the documented tolerance.
        
3.  Exclude voided transactions from duplicate matches by default unless the request explicitly supports restoring or replacing voided data.
    

The initial timestamp tolerance should be configurable and documented; a default of 5 minutes is reasonable for notification retries. Matching must use a half-open timestamp interval around the candidate.

### 9.3 Race protection

SQLite permits one writer at a time, but application-level checks still need coordination. The final duplicate search and insert must occur under the same write transaction. If a future schema adds a deterministic deduplication key, enforce it with a unique index and translate constraint failures into a duplicate result.

## 10. MCP interface

### 10.1 General conventions

Every tool returns a structured JSON object with stable field names. Dates are RFC 3339 UTC strings. Monetary values are integer minor units and are always accompanied by a currency code.
Successful mutation responses should include:

```json
{
  "status": "created",
  "transaction": { }
}
```

Errors should use a stable application code and a safe human-readable message:

```json
{
  "error": {
    "code": "category_not_found",
    "message": "The requested category does not exist.",
    "details": {}
  }
}
```

The MCP layer must not expose SQL, stack traces, filesystem paths, driver errors, or secrets.

### 10.2 Transaction tools

#### `create_transaction`

Required inputs:

```json
{
  "direction": "money_in | money_out",
  "amount_minor": 19800,
  "currency": "INR",
  "occurred_at": "2026-01-15T10:30:00Z",
  "category_id": "cat_..."
}
```

Optional inputs:

```json
{
  "description": "Grocery store",
  "original_notification": "Original notification text",
  "reference_id": "bank-reference"
}
```

Possible statuses: `created` or `duplicate`. A duplicate response must include the existing transaction and matching reason.

#### `get_transaction`

Input: `transaction_id`.
Returns the canonical transaction, including void fields when present. It may optionally include audit history only if that is explicitly part of the schema; otherwise audit retrieval should remain an internal or future tool.

#### `list_transactions`

Inputs:

```json
{
  "start": "2026-01-01T00:00:00Z",
  "end": "2026-02-01T00:00:00Z",
  "direction": "money_in",
  "category_id": "cat_...",
  "include_voided": false,
  "limit": 50,
  "cursor": "..."
}
```

Use half-open ranges: `start <= occurred_at < end`. Default ordering is `occurred_at DESC, id DESC`. Pagination must be deterministic and must not use offset pagination for the primary implementation if a cursor can be supplied.

#### `update_transaction`

Requires `transaction_id` and one or more mutable fields. The service should reject an empty patch. `original_notification` is not mutable.

#### `void_transaction`

Requires `transaction_id`; accepts optional `reason`. The result is idempotent for an already-voided transaction according to the error/status convention selected by the MCP contract.

### 10.3 Category tools

*   `list_categories`: supports `include_archived`, default false; order active categories by normalized name then ID.
    
*   `create_category`: requires `name`; returns `category_created` or `category_already_exists`.
    
*   `update_category`: requires category ID and a new name; rejects collisions.
    
*   `archive_category`: requires category ID; preserves historical associations.
    

### 10.4 Reporting tools

*   `get_daily_summary`: accepts a UTC date or explicit UTC range.
    
*   `get_monthly_summary`: accepts `year` and `month`, interpreted as a UTC calendar month.
    
*   `get_transaction_summary`: accepts a validated arbitrary half-open UTC range and optional filters.
    
*   `get_category_breakdown`: accepts a validated range and returns totals grouped by category.
    

Report outputs should include:

```json
{
  "start": "2026-01-01T00:00:00Z",
  "end": "2026-02-01T00:00:00Z",
  "currency_totals": [
    {
      "currency": "INR",
      "money_in_minor": 100000,
      "money_out_minor": 42000,
      "net_minor": 58000,
      "transaction_count": 7
    }
  ],
  "categories": []
}
```

Because multiple currencies may exist, do not sum different currencies into one net total. Category breakdowns should be grouped by currency and category.

## 11. Reporting queries and rules

All report queries must exclude `voided_at IS NOT NULL` unless an explicit administrative view is added later.
Use parameterized queries of the following form:

```sql
SELECT
    currency,
    SUM(CASE WHEN direction = 'money_in' THEN amount_minor ELSE 0 END) AS money_in_minor,
    SUM(CASE WHEN direction = 'money_out' THEN amount_minor ELSE 0 END) AS money_out_minor,
    COUNT(*) AS transaction_count
FROM transactions
WHERE occurred_at >= ?
  AND occurred_at < ?
  AND voided_at IS NULL
GROUP BY currency
ORDER BY currency ASC;
```

Category breakdown:

```sql
SELECT
    category_id,
    currency,
    SUM(amount_minor) AS total_minor,
    COUNT(*) AS transaction_count
FROM transactions
WHERE occurred_at >= ?
  AND occurred_at < ?
  AND voided_at IS NULL
GROUP BY category_id, currency
ORDER BY currency ASC, total_minor DESC, category_id ASC;
```

The service resolves category IDs to names in a deterministic way. It must define behavior for a category archived after historical transactions were recorded: historical reports continue to show the category name associated with the category record.

## 12. Error taxonomy

Define typed application errors with stable codes:

```text
invalid_request
invalid_direction
invalid_amount
invalid_currency
invalid_timestamp
invalid_date_range
transaction_not_found
category_not_found
category_already_exists
archived_category
transaction_already_voided
duplicate_transaction
empty_update
conflict
database_unavailable
migration_failed
internal_error
```

Map errors at the MCP boundary as follows:

*   Validation and not-found errors: safe client error with actionable message.
    
*   Duplicate: structured normal outcome or conflict according to the tool contract.
    
*   Database and internal errors: generic safe message, detailed structured log entry with request correlation ID.
    

## 13. Logging and observability

Use structured logs with fields such as:

```text
request_id, tool, operation, duration_ms, outcome, error_code
```

Do not log full original notifications by default. Do not log credentials, database contents, or complete request payloads. Log duplicate detections using IDs and matching reason, not sensitive message contents.
At minimum record:

*   Startup and shutdown.
    
*   Migration version and result.
    
*   Tool invocation outcome and duration.
    
*   Validation failures by code.
    
*   Duplicate outcomes.
    
*   Database busy, locked, and migration errors.

## 16. Operational requirements

*   Run under a dedicated service identity.
    
*   Restrict permissions on the database directory and file.
    
*   Back up using SQLite-aware procedures, not an unsafe copy of only the main database file during active writes.
    
*   Include the database, WAL state, and any required backup metadata in restore procedures.
    
*   Test restoration periodically.
    
*   Keep migration versions and release versions traceable.
    
*   Provide a documented way to stop the service before emergency file-level maintenance.
    

## 17. Definition of done

The v1 implementation is complete when:

1.  A clean installation creates and migrates the SQLite database successfully.
    
2.  All declared MCP tools are registered with stable schemas.
    
3.  Invalid requests are rejected without database writes.
    
4.  Valid transaction creation writes both transaction and audit event atomically.
    
5.  Duplicate retries return a structured duplicate result and do not create another record.
    
6.  Updates preserve the transaction ID and original notification text.
    
7.  Voids preserve data, generate audit history, and exclude transactions from default reports.
    
8.  Archived categories cannot be assigned to new or updated transactions.
    
9.  Reports calculate totals inside Kubera and handle currencies independently.
    
10.  Repository, service, MCP contract, and end-to-end tests pass.
     
11.  Logs do not expose secrets or unnecessary financial notification content.
     
12.  Backup, restore, migration, and graceful-shutdown procedures are documented and verified.
